# 发现

- 多模态MCP 已经初始化为独立 git 仓库，并被确认作为第一版 OpenRouter 生图 MCP 的实现边界。
- OpenRouter Reference 现阶段更适合作为参考资料来源，而不是实现根。
- 当前最关键的可行性判断不在于能否调通 OpenRouter API，而在于 MCP 返回协议能否同时支撑“在 Copilot 中直接看图”和“把图保存并再次作为 reference 使用”。
- 第一版成功标准可以进一步收窄为：MCP 能真实生成一张图、将其保存到工作区，并返回足够的结果让用户在 VS Code 内打开查看。
- 第一版范围应收束为单工具 generate_image；音频、视频和流式 partial image 都不应进入当前 MVP。
- OpenRouter 的 image generation 文档已经把纯文生图和带参考图的 image-to-image 放在同一能力面内：文本 prompt 是必填，图像参考通过可选的 input_references 数组传入。
- OpenRouter 的多模态图片输入常见载荷形态是 image_url，可承载远程 URL，也可承载 data URL；这意味着本地图片在 MCP 内转成 data URL 再上传是可行路径。
- 当前采用的稳定 TypeScript MCP SDK 1.29.0 默认请求超时为 60 秒；客户端可单独设置更长超时，也可选择在收到 progress 时重置超时，但服务端不能假定客户端启用了后者。
- 普通 MCP progress notification 只是同一次未完成调用中的状态信号，不会作为中间工具结果驱动 Agent 继续推理；因此工具描述仍需明确告知 Agent 生图通常约需一分钟且可能更久。
- 稳定 SDK 会把客户端 AbortSignal 取消包装为 McpError，并在消息中保留 AbortError；进程内协议测试已确认服务端能收到取消并终止等待。
- 当前稳定 SDK 的运行时依赖存在一项仅影响 Hono Windows 静态文件服务的中危路径穿越告警；本项目使用 macOS 本地 stdio 且不启用该 HTTP 静态服务，现阶段不为消除扫描结果而降级 SDK 或强制覆盖其主版本依赖。
- 2026-07-25 在 VS Code Copilot 中真实调用开发态探针，30、60、120 秒均在同一次工具调用内完整返回，60 秒边界未触发超时，因此首版可以采用同步等待最终图片的契约；Agent 工具接口只收到最终结果，无法据此断言用户界面是否展示了中间 progress。
- VS Code 将 MCP 显示为工作区级还是用户级，取决于配置写入位置：项目 `.vscode/mcp.json` 属于工作区级，`~/Library/Application Support/Code/User/mcp.json` 属于用户级；是否由推荐目录安装并不是决定因素，Godot 也可通过自动写入用户配置成为用户级 MCP。
- 2026-07-25 使用默认模型 `black-forest-labs/flux.2-klein-4b` 进行首次真实调用时，公开 endpoints API 仍返回 1 个 Black Forest Labs 端点和 `$0.014/MP` 定价，但生成请求返回 HTTP 404 `No allowed providers are available for the selected model`，未生成或保存文件。这表明模型“可发现”不等于当前账户与实时路由“可生成”，后续错误提示和可用性策略不能只依赖 endpoints 发现结果。
- 为了避免仓库一打开就被 VS Code 当作已安装 MCP，工作区级自动生效配置应从 `.vscode/mcp.json` 迁出；开发态可保留非自动加载模板，普通用户安装则通过显式写入 `~/Library/Application Support/Code/User/mcp.json` 完成。
- 用户级安装脚本需要只增删本项目自己的 server 与 inputs，不能覆盖 Tavily、Godot 等其他 MCP 条目；这类配置合并与卸载逻辑已单独实现并通过本地测试。
- 2026-07-25 本机已清除本项目的用户级 MCP 条目，同时仓库内也不再保留会被 VS Code 自动加载的 `.vscode/mcp.json`；后续普通用户安装验证可以从干净状态开始。
